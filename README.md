# Webagent

A Chrome Manifest V3 side-panel agent for multi-step workflows on HTTPS websites. It acts in the tab you star (★) and can read text from up to five other open tabs (+) as context, asking OpenRouter for the next move. A single reply can carry one to four actions that run back to back, so filling a form or a document does not cost a round trip per field. It drafts a 3–6 step plan before it starts, shows that plan as a checklist in the side panel, keeps it across steps and panel reloads, and only ticks an item off once a verified action backs it up — a tick you disagree with can be clicked to undo it. It can think through a plan, click, type into ordinary text fields and canvas editors such as Google Docs, read the full page text, scroll, wait for loads, navigate, press keys, and summarize. Every step lands in a timeline in the chat, with the current action pinned at the bottom while it runs. Each step sends the full action history — recent steps with their results and the page URL after each one, older steps condensed — so the agent does not forget what it already tried. It also receives an interactive-element map of the viewport (role, label, and centre coordinates) alongside the screenshot, which makes clicks far more accurate than vision alone. Every action is checked against a page fingerprint: a click or key press that changes nothing is marked *no visible change*, an unresponsive click gets one scripted fallback, and the panel re-reads the page and retries when it shifted underneath. The Worker rejects a step that repeats an action the page did not respond to and asks the model to choose differently, refuses a plan tick with no successful step behind it, and refuses a premature `done` while plan items are unchecked. **Autopilot** is on by default: each reply's actions run immediately and back to back, and the agent keeps working on its own, including clicks that may submit forms or make irreversible changes. Turn Autopilot off to review each round's actions, text and screenshot marker before they run. The Continue button now only appears when something genuinely needs you: a permission prompt, a stalled page, or a failed action. It stops after 60 actions. The Stop button prevents subsequent actions, but an action already in progress may still finish. It cannot access Chrome internal pages, and it blocks typing into password fields and forms containing password inputs. Use only on sites and tasks you are authorized to automate.

## Install the extension

Download [dist/webagent-extension.zip](dist/webagent-extension.zip), unzip it, open `chrome://extensions`, enable **Developer mode**, and choose **Load unpacked** with the extracted folder. Pin the extension and click its icon to open the side panel. This is an unpacked developer build, not a Chrome Web Store publication. For a new ZIP after editing, run `cd extension && zip -r ../dist/webagent-extension.zip .`.

The default Worker is `https://webagent.amos-donn.workers.dev`. Select a page, enter an objective, and start; webagent writes a plan first and checks items off as it works. No accounts or sign-in. The extension requests Chrome site access as needed. Autopilot may pause when it meets an origin that has not been granted yet; select Continue to grant access. In review mode, check the proposed text, destination and screenshot marker before approving. With Autopilot on, actions run immediately and may be wrong; use it only when you accept that risk. A page can change after observation, and visual coordinates can be wrong; never approve an action without checking. If a click opens a new tab, select that tab before continuing. The agent does not automatically handle CAPTCHAs, authentication, payment details, downloads, or restricted pages.

## Configure your existing Worker and D1

1. `wrangler.jsonc` identifies your existing **webagent** D1 database and binds it as `DB`. Wrangler config is the deployment source of truth; verify the ID in Cloudflare Dashboard → D1 → webagent if your database changes.
2. Apply [migrations/0001_initial.sql](migrations/0001_initial.sql) to that database once using the D1 dashboard SQL console, or from an authenticated Wrangler installation run `npx wrangler d1 migrations apply webagent --remote`. This creates the `rate_limits` table. Do not apply this to a database you did not intend to modify.
3. In Worker → Settings → Variables and Secrets, add these **encrypted secrets**:
   - `OPENROUTER_API_KEY` — your OpenRouter API key. Store it as a Worker secret, not in the extension.


   The Worker uses `google/gemini-3.5-flash-lite`: a fast, low-cost vision model that supports the image and JSON request, routed to the highest-throughput provider (`provider: { sort: "throughput" }`). To change it, add an ordinary (non-secret) variable `OPENROUTER_MODEL` — for example `openrouter/free` for a zero-cost model, or `google/gemini-2.5-flash` for more capability. The model must accept image input and JSON output. Model pricing, availability and rate limits vary.
4. In Workers Builds, use the repository root and deploy command `npx wrangler deploy`. The config sets `keep_vars` to preserve dashboard variables and secrets. Make sure the build has a supported Wrangler version and that `DB` is still bound to the intended database after deployment. Apply the migration before deploying this version. Your existing push-to-main build can deploy it once these changes are committed and pushed; this project does not push or deploy automatically on its own.
5. Open `https://webagent.amos-donn.workers.dev/health` to check that the Worker responds, then test a simple workflow in Chrome.

## Privacy and limitations

When you start or continue a workflow, visible page text (up to 40,000 characters, trimmed to 12,000 for the model), the viewport screenshot, labels and coordinates of visible interactive elements, the current URL, the objective, the plan, and previous actions are sent to the Worker and OpenRouter and the selected model provider. Screenshots can contain sensitive information even when text is hidden. Do not use sensitive pages or enter secrets in objectives. Model output and website content are untrusted: prompt injection and incorrect actions are possible, confirmation is not a guarantee of safety, and with Autopilot on there is no per-action confirmation at all. Provider keys remain on the Worker. The D1 database stores only rate-limit counters; it does not store workflows. Your plan and its checkmarks live in Chrome extension local storage, are sent to the model with each step, and are cleared with **Clear** or replaced by the next task. There is no login, so anyone with your Worker URL can spend your OpenRouter quota: keep the URL private. Rate limits are basic and should not be treated as complete abuse protection. Deploy with appropriate access, monitoring, and quota controls before sharing publicly.

Provider references: [OpenRouter free router](https://openrouter.ai/docs/guides/routing/routers/free-router), [OpenRouter API](https://openrouter.ai/docs/api_reference/overview), [Cloudflare D1 migrations](https://developers.cloudflare.com/d1/reference/migrations/), [Workers Builds configuration](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/).

## Chats, commands and approval modes

Every task is a chat. Chats are stored in Chrome extension storage (up to 20, newest first), survive closing the panel and reloading the browser, and can be reopened from the ☰ button. `Export .md` writes the current chat, its plan and its step log to Markdown, and `Delete all` clears them.

The message box understands two shortcuts: `/` opens commands (`/new`, `/chats`, `/export`, `/plan`, `/noplan`, `/auto-plan`, `/saw`, `/stop`) and `@` adds another open tab as read-only context.

A checklist is optional: the planner returns no steps for short tasks, so a one-click job runs without one. Use `/plan` to force a checklist for every task or `/noplan` to skip it.

The mode picker next to the send button mirrors the three modes Claude in Chrome offers: **Ask each round** pauses for approval, **Auto** runs freely but pauses before steps that look irreversible (paying, deleting, sending, submitting, sharing, uploading, or typing password/card-like text), and **Autopilot** never pauses. The starred tab is added to a `webagent` tab group when a task starts, and ◉ shows the exact screenshot the last decision was made from.

## Accessibility refs, safety boundary, skills, evals and the MCP bridge

**Grounding.** Every observation now includes an accessibility-tree snapshot (`Accessibility.getFullAXTree`) exposed as refs (`e12`). Actions may target `{"ref":"e12"}` instead of coordinates, which works off-screen and inside shadow roots; refs are stored per tab in session storage and expire with the page. A `fill` action sets up to 12 fields in one call.

**Context.** The screenshot is only attached when the tree is thin (fewer than 15 refs) or when the model asks with `{"needScreenshot":true}`, and each reply may carry a three-field `memory` that is fed back on the next round.

**Permissions.** Site access is one optional grant covering `https://*/*` and `http://*/*`, requested on the first task and remembered by Chrome from then on — the agent no longer asks again for each new website. Reloading or updating the unpacked extension keeps the same extension ID, so the grant survives reloads too; to revoke it, open `chrome://extensions` → Details → Site access. Separately, Chrome shows a "started debugging this browser" bar while the agent holds the debugger — that is Chrome's own notice for the `debugger` permission, not a request, and it disappears when the task stops.

**Safety.** Page text is wrapped in random `<<SNAP-…>>` delimiters, instruction-looking lines are removed before the model sees them, CSS-hidden text is dropped at extraction, cross-origin navigation extends the task's sites instead of stopping it, and consequential labels (`delete`, `pay`, `send`, …) are matched against the **intent** of your goal, the plan and the chat — not its exact wording — so "clean up my inbox" covers a Delete button. A matching step runs with a notice; only spending money or closing an account is refused (`BLOCKED_ACTION`) when autopilot runs unattended and the goal implies neither. Password fields are always blocked.

**Keyboard.** Keys are sent as real key events, so the agent can use what a person would: `/` or `s` to focus a site's search, `Escape` to close a dialog, `Tab`/`Shift+Tab`, `Space`/`Shift+Space`, `Home`/`End`, `PageUp`/`PageDown`, arrow keys, plus any printable character and chords like `Control+K`, `Shift+Tab` or `Meta+Enter`. When a nested scroller ignores programmatic scrolling, `scroll` falls back to the Space bar.

**Typed errors.** Failures return codes (`STALE_REF`, `NOT_ACTIONABLE`, `BLOCKED_ACTION`, `PAGE_CHANGED`, `NO_EFFECT`, `PASSWORD_FIELD`) which appear in the timeline and in the model's history. In Auto and Autopilot a failed step is feedback, not an ending: the run re-reads the page and tries another route (up to three consecutive retries) instead of handing control back after one obstacle.

**Skills.** `/skill` distils the current run into a named, parameterised skill (secrets listed as parameters, values never stored) and `/` lists saved skills to replay.

**Evals.** `node evals/run.mjs --validate` checks the 30-task rubric suite; grading exported chats gives pass@3.

**MCP bridge.** Enable **Local bridge** in Settings, run `node bridge/server.mjs`, then point any MCP client at `node mcp/server.mjs` to drive the tab with `browser_observe`, `browser_click`, `browser_type`, `browser_fill`, `browser_key`, `browser_scroll`, `browser_navigate`, `browser_read` and `browser_screenshot`. The bridge binds loopback only and rejects requests carrying a web Origin. Neither piece needs an account or a key.
