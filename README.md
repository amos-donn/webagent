# Webagent

A Chrome Manifest V3 side-panel agent for multi-step workflows on HTTPS websites. It acts in the tab you star (★) and can read text from up to five other open tabs (+) as context, asking OpenRouter for one action at a time. It can think through a plan, click, type into ordinary text fields, read the full page text, scroll, wait for loads, navigate, and summarize. Every step lands in a timeline in the chat, with the current action pinned at the bottom while it runs. By default it shows the proposed action and screenshot for your approval; select **Continue to next step** once the page has settled. Opt-in **Full access mode** automatically executes actions without per-action approval, including clicks that may submit forms or make irreversible changes. It stops after 30 steps. The Stop button prevents subsequent actions, but an action already in progress may still finish. It cannot access Chrome internal pages, and it blocks typing into password fields and forms containing password inputs. Use only on sites and tasks you are authorized to automate.

## Install the extension

Download [dist/webagent-extension.zip](dist/webagent-extension.zip), unzip it, open `chrome://extensions`, enable **Developer mode**, and choose **Load unpacked** with the extracted folder. Pin the extension and click its icon to open the side panel. This is an unpacked developer build, not a Chrome Web Store publication. For a new ZIP after editing, run `cd extension && zip -r ../dist/webagent-extension.zip .`.

The default Worker is `https://webagent.amos-donn.workers.dev`. Create an account using the invitation code, or sign in. Select a page, enter an objective, and start. The extension requests Chrome site access as needed. Full access may pause when it encounters an origin that has not yet been granted; select Continue or approve the navigation to grant access. In review mode, review the proposed text, destination and screenshot marker before approving. In full access mode, actions are automatic and may be wrong; use it only when you accept that risk. A page can change after observation, and visual coordinates can be wrong; never approve an action without checking. If a click opens a new tab, select that tab before continuing. The agent does not automatically handle CAPTCHAs, authentication, payment details, downloads, or restricted pages.

## Configure your existing Worker and D1

1. `wrangler.jsonc` identifies your existing **webagent** D1 database and binds it as `DB`. Wrangler config is the deployment source of truth; verify the ID in Cloudflare Dashboard → D1 → webagent if your database changes.
2. Apply [migrations/0001_initial.sql](migrations/0001_initial.sql) to that database once using the D1 dashboard SQL console, or from an authenticated Wrangler installation run `npx wrangler d1 migrations apply webagent --remote`. This creates `users`, `sessions`, and `rate_limits` tables and an index; it does not create user accounts. The extension signup creates account rows. Do not apply this to a database you did not intend to modify.
3. In Worker → Settings → Variables and Secrets, add these **encrypted secrets**:
   - `OPENROUTER_API_KEY` — your OpenRouter API key. Store it as a Worker secret, not in the extension.
   - `SIGNUP_INVITE_CODE` — a long random invitation code you choose. Anyone with this code can create an account and use your OpenRouter quota; share it only with trusted users.

   The Worker uses `openrouter/free`, which routes to a free model compatible with the image and JSON request. It does not fall back to paid models. Free model availability, quality, and rate limits vary; workflows can fail or pause when a compatible model is unavailable. No Gemini or Roboflow key is needed.
4. In Workers Builds, use the repository root and deploy command `npx wrangler deploy`. The config sets `keep_vars` to preserve dashboard variables and secrets. Make sure the build has a supported Wrangler version and that `DB` is still bound to the intended database after deployment. Apply the migration before deploying this version. Your existing push-to-main build can deploy it once these changes are committed and pushed; this project does not push or deploy automatically on its own.
5. Open `https://webagent.amos-donn.workers.dev/health` to check that the Worker responds, then test account creation and a simple workflow in Chrome.

## Privacy and limitations

When you start or continue a workflow, visible page text (up to 40,000 characters), the viewport screenshot, the current URL, the objective, and previous actions are sent to the Worker and OpenRouter and the selected model provider. Screenshots can contain sensitive information even when text is hidden. Do not use sensitive pages or enter secrets in objectives. Model output and website content are untrusted: prompt injection and incorrect actions are possible, and confirmation is not a guarantee of safety, and full access removes per-action confirmation entirely. The account session token is stored in Chrome extension local storage; provider keys remain on the Worker. The D1 database stores account credentials as salted PBKDF2 hashes, session token hashes, and rate-limit counters; it does not store workflows. Invitations are shared secrets, not email verification or a full public signup system. Rate limits are basic and should not be treated as complete abuse protection. Deploy with appropriate access, monitoring, and quota controls before sharing publicly.
